The trade-off that defines the engine

HNSW answers queries by walking a graph. Two knobs decide how well it does: M, how many neighbours each node keeps, fixed when the graph is built; and ef_search, the beam width at query time. Widening the beam buys recall and costs throughput — every curve below is that same trade, drawn for four graph densities.

Recall against throughput

100 000 × 128-d, L2, ef_construction 200, single thread, AVX2 · each point is one ef_search
Denser graphs win at the high-recall end and lose at the cheap end. At recall 0.99, M=32 serves about 11 400 queries/s where M=8 manages roughly 5 300 — but at recall 0.52 M=8 is the fastest thing on the chart. The cost of density is paid once, at build time.

What the AVX2 kernels are worth

Distance kernels are compiled for both tiers and picked at runtime from CPUID, so one binary runs everywhere. The gain grows with dimension: at 128 components the loop is short enough that overhead dominates, and by 1536 the vector unit is doing almost all the work.

Concurrency, including where it stops helping

Builds parallelise well. Searches do not, past a point: once the working set outgrows cache the workload is memory-bound, and adding threads buys progressively less.

Speedup against one thread

The drop for flat search at 16 threads — 6.1× at 12 threads, 2.70× at 16 — is in the committed results and is left as measured. The suite README puts it down to a noisy desktop machine with 8 physical cores; it is not presented as a property of the engine.

The on-disk format

A .vfidx file is a header plus typed sections, each covered by a CRC-32C. Vectors start on a 4096-byte boundary so a whole-file mapping hands back aligned rows and the loader can skip reading them entirely.

Section layout

graph sections present only for an HNSW collection
Loading can memory-map the vectors instead of copying them, so a cold open is dominated by the graph sections rather than by N × D × 4 bytes. Corruption is caught rather than trusted: the persistence suite covers truncation, bit flips, and hostile values that carry a valid checksum.

What these numbers do not cover

  • One machine, one run each. An AMD Ryzen 7 4800H laptop — 8 cores, 16 threads, 15.4 GB, Windows 11, MSVC Release. Nothing here is a cross-platform or cross-CPU comparison.
  • Synthetic data. Gaussian-mixture vectors, seed 1, 100 clusters. No real-world embedding set has been measured, and real data has structure that changes recall.
  • Single node, single process. No replication, no sharding, no distributed anything.
  • Recall falls with scale at a fixed beam: at 1 M × 128-d, ef_search = 64 gives recall 0.79, and reaching 0.95 needs 256. Larger collections need a wider beam, not the defaults tuned at 100 K.
  • Timing figures were taken on a desktop OS with other processes live; the thread-scaling tail above 12 threads is visibly noisy.
